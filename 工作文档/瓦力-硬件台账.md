## 一、引脚真相表（**实测优先**，作者资料只作参考）

### 1.1 实测结论（2026-10-22，`pin_scan` v6 逐脚驱动 + 看实物）

| GPIO | 实测结果 | 作者资料说 | 是否一致 |
|---|---|---|---|
| **13** | **电机 A 的一路**（方向正确） | 左轮后退 `MOTOR_LB` | ✅ 是电机之一 |
| **14** | **电机 A 的另一路**（方向正确） | 右轮前进 `MOTOR_RF` | ✅ 是电机之一 |
| **17** | **电机 B 的一路**（方向正确） | 未使用 | ❌ 作者未定义 |
| **18** | **电机 B 的另一路**（方向正确） | **灯** `LAMP_GPIO` | ❌ **完全不符** |
| 12 | **无反应**（这块板没接） | 左轮前进 `MOTOR_LF` | ❌ |
| 21 | **无反应**（这块板没接） | 右轮后退 `MOTOR_RB` | ❌ |
| 1 / 2 / 3 | 无反应 | 未使用 / 老版 RB | — |
| 4–11 / 15 / 16 / 38–48 | 无反应（见 §二 舵机未找到） | 音频 / 按键 / 屏 | — |

**⇒ 这块板的真实电机接线：`电机A = GPIO13 + GPIO14`，`电机B = GPIO17 + GPIO18`。**

### 1.2 这条实测解释了两个悬案

1. **"说开灯，一个电机转、灯不亮"** —— `self.lamp.turn_on` 驱动的是 `GPIO18`（作者定义的灯），
 而这块板的 GPIO18 是**电机 B 的一路 IN**。所以"开灯"实际是"给电机 B 通电"，灯自然不亮。
 **卖家固件里的 lamp 功能在这块板上是错的**（作者资料与实物引脚对不上）。
2. **"8 个脚全没反应" → 后来"最后 4 个有反应"** —— 板上有**电源开关**：
 不打开也能连 COM（逻辑由 USB 供电），**打开才给电机供电**。之前测试没开开关。

## 二、舵机：代码里没有（**必须现场核对**）

- 用户口述：瓦力有 **3 个舵机**。
- 事实：**作者仓库 113 块板里，只有 `electron-bot` 有舵机代码，`qebabe-xiaoche` 一行都没有**；板子里那份固件的 dump 里也 grep 不到 `servo`/`SG90`。

三种可能，**不能猜，要现场看**：

1. 3 个舵机是**配件/结构件**（云台、手臂），当前固件根本没驱动它们 ⇒ 装回去也不动，属正常；
2. 瓦力是**后续硬件版本**，作者另有一版固件（当前板子里是旧版）；
3. 记混了（3 个"舵机"其实是别的件）。

**判据**：上电后舵机三根线有没有 PWM 信号（示波器/万用表 AC 档），或者干脆看它会不会自己回中位。**不动 + 无声 = 没被驱动**。

### 2.1 实测（2026-10-22）：28 个候选脚挨个给 50Hz/1.5ms 脉冲，**舵机没有任何反应**

候选集：`1..18, 21, 38..42, 45..48`（排除 0=BOOT、19/20=USB、26-37=Flash/PSRAM、43/44=UART0）。
每个脚给 2 秒 50Hz/1.5ms 脉冲（舵机中位 90°），观察是否有回中/抖动 —— **全无**。

⇒ 三种可能，按可能性排序：

| # | 可能 | 怎么验 |
|---|---|---|
| 1 | **舵机没供电**（舵机 5V 与电机供电不是同一路，或没接） | 打开电源开关后，**用手轻转舵机臂**：有阻力/回弹 = 通电；很松 = 没通电 |
| 2 | 舵机信号接在**被排除的脚**上（`43/44` 或 `19/20`） | 43/44 可以试（console 走 USB，风险低）；**19/20 绝对别驱动**（USB D-/D+，一动就掉线） |
| 3 | 舵机信号走 **I2C 舵机驱动板**（如 PCA9685 @0x40，挂在屏的 I2C 41/42 上） | 扫 I2C 看有没有 0x40/0x41… 地址 |
| 4 | 这 3 个"舵机"其实是别的件（记混） | 看实物丝印 |

> 注意：作者固件里**没有舵机代码**，所以就算舵机接好了也不会动 —— 想动必须我们自己写 PWM 输出。

### 2.2 已找到的舵机（实测，2026-10-22）

| GPIO | 实测 |
|---|---|
| **GPIO11** | **左手舵机**（v8 全自动扫描时，给 50Hz 来回扫脉冲，左手会动） |
| **GPIO12** | **右手舵机** |
| 第三个舵机 | **挂起**（用户决定不追，不浪费时间） |

- 其余非电机脚扫过，无反应
- 注意：`GPIO11` 在作者 `config.h` 里**没有任何定义**；`GPIO12` 作者写的是"左轮前进"，实际是右手舵机

### 2.3 ★ 结论：这块板的**接线和它自己固件的引脚对不上**

原厂固件（`qebabe-xiaoche`，作者开源那份）按 `config.h` 驱动 `12/13/14/21`（电机）+ `18`（灯）。
但这块板实物是：电机 A=`13/14`、电机 B=`17/18`、舵机=`11/12`。

⇒ 所以原厂固件在这块板上的表现**必然是错的**，这解释了之前所有怪现象：

| 现象 | 原因 |
|---|---|
| 网页点"前进/后退"只有一个电机动 | 前进=L(12)+R(14)、后退=L(13)+R(21)；这块板只有 13/14 是电机，所以同一台电机被"前进"和"后退"各驱动一次 |
| 说"开灯"→ 一个电机转、灯不亮 | `lamp` 拉高 `18`，而 18 是电机 B 的一路 IN |
| 3 个舵机从来不响应语音/动作 | 固件里根本没有舵机代码，且信号在 11/12（固件当成电机前进脚） |

**⇒ 想让瓦力功能正确，必须自己写板级代码（`wali` 板），不能靠原厂固件。**

## 三、测试顺序（**先用板上现有固件，不用我们编**）

原厂固件自带**网页控制台**，这是最省力的验法：

1. **上电 → 看屏**：OLED 应显示状态（配网二维码/表情/文字）。不亮 ⇒ 查 41/42 两根线 + 3V3。
2. **配网**（按原厂流程）；连上后**用网页控制台**（`/api/motor/action`）点：
 - 前进 / 后退 → 两个轮子是否同向
 - 左转 / 右转 → 差速是否成立
 - 灯开 / 灯关（MCP `self.lamp.turn_on`） → 灯是否亮
3. **喇叭**：让它说话（音量 +/− 也能验按键）。
4. **麦克风**：说唤醒词，看是否响应。
5. **只在这时才需要我们的自检固件**：怀疑某一路不通、或网页控制不直观时。

> 已知坑（作者自己在 config.h:60 写过）：右轮后退原本在 **GPIO3（strapping 脚）**，会干扰启动。若你量到接的是 3，上电可能起不来 —— 这本身就是个"已发生的故障"。

### 6.1 两个"唤不醒"的真根因（都已修）

1. **分区表缺 `model` 分区** → 启动报 `MODEL_LOADER: Can not find model in partition table`，唤醒词模型没打包。
   ⇒ 新建 `partitions\wali_16m.csv`（model 960KB + ota 2×3MB + assets 6MB）。修好后日志出现 `Successfully load srmodels`。
2. **`audio_service.cc` 里有一段 MOSS 时期的"强制关麦"补丁**（启动后无条件 `codec_->EnableInput(false)`，日志 `🔇 麦克风已强制关闭`）
   → 麦克风一上电就关死，任何板子都唤不醒；随后 `AudioInputTask` 报 `Should not be here, bits: 4` 并退出。
   ⇒ 已删除。它**不是** §七 设计的"软开关"，只是占位。

### 6.2 BOOT 键行为（容易误会）

| 操作 | 结果 |
|---|---|
| **单击 BOOT** | 开始/结束对话（会打断唤醒检测） |
| **长按 BOOT**（≥2 秒） | **重新配网**（进 AP 模式）→ 这时唤不醒是正常的 |
| 重新上电 | 恢复正常，可唤醒 |

### 6.3 官方云绑定状态（2026-10-22）

- 设备 UUID `47c74e50-0fc0-4b55-b767-db867e95c1b3`，在官方云**仍是"已激活"**状态
- 用户在控制台删掉了原来的智能体 ⇒ 设备不弹激活码，控制台里也看不到它
- 想重新绑定新智能体：**先清 NVS**（`esptool erase_region 0x9000 0x4000`，只清 WiFi+激活，不动固件）→ 长按 BOOT 配网 → 屏幕给新激活码 → 控制台输入
- **结论：这条不用折腾了** —— 反正要接自建后台
