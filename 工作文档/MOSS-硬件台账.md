## 一、板子是什么

**MOSS 550W = 核心板 + 5 组排针**。屏幕、麦克风、灯带**都不在板上**，全靠排针外接。

| 器件 | 用途 | 备注 |
|---|---|---|
| U8 ESP32-S3-WROOM-1-N16R8 | 主控 | 16MB Flash / 8MB PSRAM |
| U6 74HC595 + U7 ULN2003 + U9 | 电机 1 驱动链 | 5 脚座，另有 CN3 备用 |
| U10 74HC595 + U11 ULN2003 | 电机 2 驱动链 | 5 脚座，另有 CN4 备用 |
| U12 NS4168 | I2S 功放 | 喇叭 CN5 / J2 |
| FPC1(26) + U13(20) + H1(40) | 摄像头 DVP + SCCB | |
| U4 + Q1/Q2 + D1/D3 + SW1 | 充电 / 升压 / 电源开关 | 电池 CN1/J1，USB CN2 |
| FMLED1–5 + FMH1/FMH2 | 板上 5 颗灯珠 | 数据线只到焊盘 |

**排针定义（网表核实）**

```
H2: GPIO13 / 3V3 / GND          麦克风 PDM 时钟
H3: GPIO12 / GPIO14 / GND       麦克风 PDM 数据 / 备用
H4: GPIO02 / GPIO01 / 3V3 / GND 屏幕（4 线 I2C）
H5: +5V / GPIO07 / GND          灯带 1 数据
H6: +5V / GPIO48 / GND          灯带 2 数据
```

## 三、已结案（结论 + 证据）

### ① I2C 引脚定义 —— 结案，别再改
自检 A（`SDA=2 SCL=1`）扫到 `0x3C`；自检 B（`SDA=1 SCL=2`）**一个设备都没有**。
⇒ 反向对照成立，`config.h` 的写法正确。

### ② 步进电机 ×2 —— 通过
两台电机在自检第 3、4 项都能正转 128 步，`步进→释放` 实测 **2230 ms / 2140 ms**
（设定 60 步/秒 → 理论 2133 ms），速度准确。
⇒ 74HC595 / ULN2003 / 24BYJ48 全链正常。

### ③ 屏幕上 —— ⚠️ **重大修正：`0x3C` 不是屏，是摄像头**

**原判断（已推翻）**：扫到 `0x3C` ⇒ 屏活着、只缺驱动。

**推翻依据（2026-10-22）**：
1. 板上一颗显示器件都没有（网表 590 个器件里没有 LCD/OLED 驱动 IC）
2. `0x3C` 就挂在 GPIO2/1 这条 I2C 上，而这条总线在本板上只连到 **U13（摄像头座）**
3. **`0x3C` 正是 OV5640 的 SCCB 地址**（OV2640 才是 `0x30`）
4. 用户刷回**原厂固件**、去掉延长线后，**摄像头工作正常** ⇒ 摄像头一直都在总线上

⇒ 结论改成：**`0x3C` = 摄像头**。MOSS **没有内置屏幕**，H4 上的 I2C 只是把总线引出来（可外挂 OLED）。
所以"屏幕不亮"这件事，前提就该是"有没有接屏"——**没接屏就不存在"不亮"**。

### ③-2 屏幕 —— ✅ **2026-10-31 已解决**（我们自己的固件现在能驱动它）

**结论**：屏是**外挂的 4 线 I2C OLED（SSD1306）**，挂 H4（`GPIO01/GPIO02`），
我们的固件已按标准三件套实现（`InitializeDisplayI2c` → `InitializeSsd1306Display` → `GetDisplay`），
**实测点亮并正常显示**。

| 项 | 值 | 证据 |
|---|---|---|
| 驱动 IC | **SSD1306**（不是 SH1106/ST7789） | 原厂镜像里有 `Install SSD1306 driver` / `SSD1306 driver installed` / `Adding OLED display` / `Turning display on`；`SH1106`/`ST7789` 零命中 |
| 总线 | I2C port **0**，SDA=**GPIO2**、SCL=**GPIO1**（外部 1k 上拉） | `config.h` + 网表 |
| 地址 | **0x3C** | 实测：`esp_lcd_panel_init` 成功、屏有显示 |
| 尺寸 | 128×64 | `config.h`；显示正常（无"只显示一半"现象） |
| 字体 | 20px（`font_puhui_basic_20_4`） | 原厂资源里是 `puhui_common_20_4.bin`，同为 20px |

**为什么以前"屏一直黑"**：不是硬件问题，也不是"用了 0 引脚"——
是**我们的板级代码 `GetDisplay()` 直接返回 `nullptr`**（见 `doc\新建文件夹\moss_550w_fix_report.md`："无显示"），
那块屏从来没被初始化过。原厂固件有 OLED 驱动，所以原厂固件下它是正常的。

⚠️ **`0x3C` 归属要重新理解**：SSD1306 默认地址也是 **0x3C**，与摄像头 OV5640 的 SCCB 地址相同。
既然现在我们的固件初始化 OLED 后屏能正常显示，说明**总线上 0x3C 确实有 OLED 应答**。
当年 selftest 扫到 0x3C 就断言"是摄像头"，现在看**至少不能排除它是这块 OLED**（"扫到地址 ≠ 知道是谁"）。
⇒ **同时插摄像头 + OLED 会有地址冲突风险**，这是接下来做摄像头必须先解决的点。

### ④ 摄像头 —— ✅ **正常**（原厂固件下已验证）**最终状态**：刷原厂固件 + **不用延长线**（直接插板上座）⇒ **摄像头正常工作**。

**中间的两条错判（都记下来防复发）**：
- ❌ "摄像头不在总线上"——错。`0x3C` 就是它，一直在应答
- ❌ "FPC1 与 MCU 不通所以扫不到"——结论方向对（FPC1 确实不接 MCU），但**用错了证据**：摄像头根本不在 FPC1 上

**硬事实（网表，可信）**：
- `FPC1`（0.5mm 26 针）的信号 `NET_8…NET_26` **只到 H1 排针，与 U8 无一相连**
- 摄像头信号走 **U13（2×10 / 20 针 / 2.54mm）**：`CAM_VSYNC/HREF/XCLK/PCLK/D0-D7/PWDN/RST` + `GPIO01/GPIO02`(SCCB)
- `CAM_LDO_CE` 不经 MCU（只有 R22 等），摄像头 LDO 常开

⇒ 摄像头**必须**插 U13 那个 20 针座，不要插 FPC1。

### ⑤ 灯组 —— ✅ **2026-10-31 已解决（改法）**（原两组已坏，改用新 WS2812 灯珠）

**硬件结构（网表）**

| | 3 灯组 | 2 灯组 |
|---|---|---|
| 灯珠 | FMLED1/2/3 | FMLED4/5 |
| 封装 | **2020**（`config.h` 里误叫 `LED_1313`） | 4020 |
| 供电网 | `5V_LED2020` | `5V_LED4020` |
| 数据入口 | `NET_1` ← `FMH1.2` | `NET_2` ← `FMH2.2` |
| 排针 | **H5**（+5V / GPIO7 / GND） | **H6**（+5V / GPIO48 / GND） |
| GPIO | **GPIO7** | **GPIO48** |

**两条供电网（`5V_LED2020`/`5V_LED4020`）在板上都没有电源来源器件** ⇒
灯珠的 5V 必须从 `FMH` 焊盘灌进去，即 `H5↔FMH1`、`H6↔FMH2` **三根线 1:1 对接**。

**实测记录**
- 2026-10-19/20：3 灯组（GPIO7）在真 WS2812 驱动下**正常点亮** ⇒ `led_strip` + RMT + 该链全通
- 2 灯组（GPIO48）**不亮** ⇒ `H6 ↔ FMH2` 至少缺一根（最可能是 +5V）
- 2026-10-22（用户报告）：**3 灯组也被弄烧**（现只剩 1 颗亮绿或蓝，后两颗不亮）⇒ 该链中途断了

**⚠️ 判断修正**：曾判定"3 灯组烧了"，实际它一度正常；也曾判定"两组都没接 GPIO"，实际 GPIO7 那组是通的。
⇒ 网表只能证明"没有铜箔走线"，证明不了"有没有锡桥/跳线"。**实物优先。**

## 五、自检怎么用

```
上电 → 自动跑 0/6 并停住
单击 BOOT（<0.8s）  = 翻到下一项（只打印标题，不执行）
长按 BOOT（≥0.8s）  = 执行当前项
判据：出现 ">>> 执行: x/6 ..." 才算真执行
```

| 项 | 内容 | 判据 |
|---|---|---|
| 0/6 | 芯片 / MAC / 堆 / PSRAM | 能看到字 = 芯片在跑、串口通 |
| 1/6 | I2C 扫描 SDA=2 SCL=1 | 扫到 `0x3C` = **摄像头**（OV5640 地址），不是屏 |
| 2/6 | I2C 扫描 SDA=1 SCL=2（对照） | 应扫不到（若也扫到，说明扫描代码有 bug） |
| 3/6 | 电机 1 正转 128 步 | 转了 = 电机链通 |
| 4/6 | 电机 2 正转 128 步 | 同上 |
| 5/6 | GPIO7/48 翻转 | 只验引脚不被人占；静态电平不会点亮 WS2812 |
| 6/6 | ADC：电池 GPIO8 / USB GPIO6 | 拔插 USB 看 USB 列变化 |

### ⑧ 步进电机 ×2 —— ✅ **2026-11-01 打通（后台可控）**

**背景**：此前电机只能靠自检固件驱动，应用层**没有入口**（`board_moss_550w.cc` 只 include 了
`motor_control.h`，没覆写任何运动接口）。2026-11-01 新增芯片级动作 `stepper`：

```json
{"type":"stepper","motor":0,"steps":64,"speed":60,"release":true}
```

| 字段 | 含义 |
|---|---|
| `motor` | 0 = **垂直轴**，1 = **水平轴**（实测，见下表） |
| `steps` | 带符号：正 = CW，负 = CCW；固件上限 ±1024 |
| `speed` | 步/秒，缺省 60，上限 400 |
| `release` | `true`（缺省）= 走完断电松劲；`false` = 保持力矩 |

**方向映射（2026-11-01 实物实测，用户观察）**

| 指令 | 实物结果 |
|---|---|
| `motor=0, steps=+64` | 垂直电机 **向后仰** |
| `motor=0, steps=-64` | 垂直电机 **向前俯** |
| `motor=1, steps=+64` | 水平电机 **向左** |
| `motor=1, steps=-64` | 水平电机 **向右** |

**三条必须记住的限制**

1. **开环无回零**：没有编码器、没有限位开关；`motor_get_position()` 只是上电以来的步数计数
   （`uint16_t`，复位即归零）。⇒ 后台**不能**假设"现在在中间"，动作只能是"相对走 N 步"。
2. **走完缺省断电**：固定步数走完会 `motor_release()`（线圈失电）。
   ✅ **垂直轴断电不会回落**（2026-11-01 用户实测，机构自锁）⇒ 不需要靠通电保持力矩，
   默认 `release:true` 即可，不必白发热。确实需要顶住时再发 `release:false`。
3. **不能用 `gpio`/`pwm` 代替**：一步 = 26 次电平操作（8 位 × SER/SRCLK + RCLK），
   且两台电机共用同一个 595 的 8 位字节（低半字节=电机1、高半字节=电机2），
   后台从外面打电平会踩掉另一台的相位。与 `ws2812` 属同一类"协议型器件"。

**标定（2026-11-01 实测）**

| 项 | 实测值 |
|---|---|
| 512 步 ≈ | **30°** |
| 一圈 ≈ | **6144 步**（1° ≈ 17 步） |
| 固件上限 ±1024 步 ≈ | ±60° |
| 剧场够用的幅度 | 64~256 步（≈ 4°~15°），不必大角度 |

**待办**：测高速（speed 200~400）是否丢步；水平/垂直各自的安全行程（有没有机械限位）。

## 九、判断修正记录（**防止按错结论去维修**）

| 曾经的判断 | 谁提的 | 实测结果 | 教训 |
|---|---|---|---|
| 3 灯组烧了 | 用户 | 它一度正常点亮，真正不亮的是 2 灯组 | 先量通断再下"烧了"的结论 |
| 摄像头是延长线/接触问题 | 用户 | 是同一件事：真凶在**接插件**，换掉延长线后好了 | 抱死一个假设会漏掉"接错座"这种可能 |
| `0x3C` 是 OLED 屏 | AI | 是摄像头（OV5640 的 SCCB 地址） | 扫到地址不等于知道是谁，要看板上有没有那个器件 |
| FPC1 不接 MCU ⇒ 摄像头扫不到 | AI | 前半对（FPC1 确实不接 MCU），后半错（摄像头不在 FPC1 上） | 结论方向对也可能是用错证据凑出来的 |
| 两组灯都没接 GPIO | AI（网表推断） | GPIO7 那组是通的 | **网表只能证明"无铜箔走线"，证明不了"无锡桥/跳线"** |
| 换了不同颗数的灯带，原厂跑马灯就"坏一半" | 用户/AI 都疑惑过 | 原厂固件把 `(GPIO, LEDs 颗数)` 写死在配置里；换颗数它就对不上 | 灯只显示收到的帧，**图案/颗数是固件的事**——这正是我们做 `ws2812` 芯片级动作的理由 |
