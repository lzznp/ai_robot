## 1. 先分清三个东西（这是所有混乱的源头）

| # | 是什么 | 谁启动 | 持有状态 | 与其他两方的关系 |
|---|---|---|---|---|
| A | **后台服务** `app.py` | 你（PyCharm），一个进程 | 内存里的 `DeviceManager`（设备 ws 连接表） | 唯一能跟设备说话的一方 |
| B | **控制台** `web_console/`（Streamlit） | 你（另一进程） | 无（session_state 易失） | **拿不到 A 的内存** |
| C | **设备固件** | 板子上电 | 自己的任务队列 | 只认 JSON，不认语义 |

⇒ **铁律 1**：控制台只能两条路拿数据 —— ① **直读同一个 SQLite**（`xiaozhi-server\data\ai_robot.db`）② **HTTP 打 8004**。
⇒ **铁律 2**：控制台**禁止** `import DeviceManager` / `core.providers` / `core.command_sender`（跨进程拿不到对象）。
违反这条的现存死代码：`web_console\services\device_service.py`、`services\command_service.py`、`utils\api_client.py`（空文件）、`pages\设备与能力管理.py`（未挂导航）。

**端口分工**：8000 = 设备 websocket ／ 8003 = OTA + `/mcp/vision/explain` ／ 8004 = 指令与控制 API。
**本机 IP**：`192.168.199.106`（页面里现在写死的就是它）。

**启动坑（2026-11-01 已修）**：`opuslib_next` 用 `ctypes.util.find_library("opus")` 找 **`opus.dll`**，
那是**按 PATH 逐个目录找 .dll** 的（`opuslib_next/api/__init__.py:9`）。conda 把 dll 放在
`<env>\Library\bin`，这个目录只在 `conda activate` 之后才进 PATH ——
所以**从 IDE / 直接调 python.exe 启动就会报 `Could not find Opus library`**。
现在 `app.py` 顶部有 6 行 bootstrap，用 `sys.prefix` 推出 `Library\bin` 并加进 PATH + `add_dll_directory`，
谁启动都一样（不写死盘符，Linux 上自动跳过）。**别再靠"记得手工加 PATH"**。

**控制台（Streamlit）启动**：`web_console\app.py` 已**不再用第三方 `st_pages`**
（它在某些情况下会抛 `'StreamlitPage' object has no attribute '_title'`，因为 Streamlit 的
`StreamlitPage.__init__` 在没有脚本上下文时会提前 return，`_title`/`_page` 都没赋值），
改成原生 `st.Page` + `st.navigation`；`config/pages.toml` 仍是唯一导航配置，
且**不再依赖工作目录**（按 `__file__` 定位 toml）。
起法：`<env>\python.exe -m streamlit run app.py`；PyCharm 用 `Module name=streamlit` + `Parameters=run app.py`。
⚠️ 本机 PATH 上的 `streamlit` 命令属于 **Python 3.13（streamlit 1.56）**，不是 lzluck（1.55）——
两套都能跑，但**别混着用**，控制台统一用 lzluck 起，免得再出现"我没改它自己坏了"。

## 2. 数据模型（4 张表，SQLite）

| 表 | 作用 | 关键列 | 谁写 | 谁读 | 当前行数 |
|---|---|---|---|---|---|
| `devices` | **设备登记**（不是在线表！） | `id`=MAC、`alias`、`device_type`、`online`、`last_seen` | 设备管理页 | 能力库/场景编排下拉 | **2** |
| `device_capabilities` | **能力库**（语义→指令） | `id`、`device_id`、`name`、`command`(TEXT)、`capability_type`、`llm_visible` | 能力库页 | 将来的 SceneDispatcher | **0** |
| `scene_templates` | 场景 | `id`、`name`、`is_active`、`prompt_context` | 场景编排页 | 后台连接时 | **4**（激活：`scene_20260718_220013`） |
| `template_role_configs` | 角色 → 设备 | `template_id`、`role_name`、`device_id`、`personality` | 场景编排页 | `connection.py:181` | **7**（激活场景 3 个：双目屏 / 月球车 / Doly） |

三条必须记住的事实：

1. **`devices.online` / `last_seen` 是死字段**（现在全 0 / null）。真实在线状态只在 A 的内存里，唯一出口是 `GET /api/devices`（只返回在线设备，无别名）。**页面拿“在不在线”必须打这个接口。**
2. **`device_capabilities.command` 是 TEXT**：写入时 `json.dumps`，读出时是**字符串**。任何地方要用它都必须 `json.loads`。现在 `能力库管理.py:209` 直接把它当 dict 当 command 发 → 会被 `/api/command` 的类型校验拒掉（400）。
3. **`template_role_configs` 与 `devices` 会不同步**：Doly（`58:e6:c5:11:e8:60`）在角色映射里，但 `devices` 里没有它 → 别名会退化成 MAC。MOSS / 瓦力 两边都没有。
4. **外键是真的生效的**（`database.py:38` 开了 `PRAGMA foreign_keys = ON`）：
   - `device_capabilities.device_id` → `devices(id)` ON DELETE **CASCADE**
   - `template_role_configs.device_id` → `devices(id)` ON DELETE **CASCADE**
   ⇒ **没登记的设备，建不了能力、也进不了角色**（`CapabilityRepo.create` 会抛 IntegrityError）。
   ⇒ 而且库现在**已经有一条 FK 违例**：`pragma foreign_key_check` 报 `(template_role_configs, 7, 'devices', 0)` —— 就是 Doly 那条角色行。
   **结论（影响工作流）：登记设备是能力沉淀的前置；测试时顺手登记，正好把这条坏数据一起修掉。**

## 3. 三条链路（现状：一条能用、一条残缺、一条不存在）

### 链路 A ｜测试链（**现在唯一能跑通的，本次主力**）

```
Streamlit 页面 → POST :8004/api/command {device_id, command}
   → command_api.py:58  dm.send(device_id, command)     # 原样转发，不校验、不包装
   → device_manager.py:62  ws.send(json.dumps(command))
   → 固件 application.cc:590  type=="command" → ExecuteCommand(payload)
   → 任务队列逐个执行 → 串口日志 → 实物动作
```
- **后台不包信封，谁发谁包。** `/api/command` 的 `command` 必须已经是 `{"type":"command","payload":{…}}`。
- 前置校验只有一条：`dm.is_online(device_id)`，不在线直接 404。
- 返回值 `success:true` **只代表 ws 写成功**，不代表设备执行了。

### 链路 B ｜对话链（有，但产出不了芯片级动作）

```
/api/text（或语音）→ connection.test_scene_dispatcher → SceneDispatcher.process
   → LLM 出文本 → actions=[{type:"tts"}] → dispatch_actions
   → connection_handler.tts.tts_one_sentence(...) → 后台合成音频 → 设备说话
```
- `process()` 只会造 **tts**（`scene_dispatcher.py:124`）；`dispatch_actions()` 只认 `tts/emotion/action`（`:148-195`），**`gpio/pwm/ws2812/camera` 一个都不认**。
- `tts` 分支用的是**当前连接那台设备**的 TTS，不看 `action["target"]`（`:168`）→ 多机剧场会串台。

### 链路 C ｜能力链（**目标，尚不存在**）

```
场景/LLM/页面 → 选角色 role → 查 template_role_configs 得 device_id
   → 从 device_capabilities 取该能力的 payload → 包成 command 信封 → dm.send(target)
```
缺口：能力库 0 行 + `▶` 坏 + 没有任何代码读 `enabled_capability_ids`。

## 4. 动作词汇表（★ 单一真相源；字段与日志全部对照过源码）

**信封（固定，不可变）**

```json
{"type":"command","payload":{
   "tts":"可直接播报的文本（可选）",
   "emotion":"happy（可选）",
   "actions":[ {"type":"…"}, … ]
}}
```

**可选动作（后台可以用的 8 个）**

| type | 必填字段 | 可选字段 | 固件执行判据（串口原样） | 实物判据 |
|---|---|---|---|---|
| `ws2812` | `pin` | `count`(缺省 **1**)、`rgb:[r,g,b]` 或 `r`/`g`/`b`、`duration` | `[WS2812] 新建灯带 pin=5 count=1` → `[WS2812] pin=5 count=1 rgb=(64,0,0)` | 灯变色；带 `duration` 到点自动 `rgb=(0,0,0)` |
| `gpio` | `pin`、`level`(0/1) | `duration` | `GPIO 17 -> 1 (hold 1200 ms)` | 万用表/继电器/蜂鸣器 |
| `pwm` | `pin` | `freq`、`pulse_us` **或** `duty`(二选一，都给则 `pulse_us` 优先)、`duration` | `[PWM] pin=32 freq=50 pulse_us=2000 bits=14 duty=…` | 舵机转到角度 / 电机转 |
| `camera` | — | `op` = `capture`(缺省) / `explain` | `[CAMERA] 抓帧开始 (op=capture)` → `[CAMERA] 抓帧成功`；无摄像头的板打 `[CAMERA] 这块板没有摄像头` | 无（靠日志） |
| `stepper` | `motor`、`steps`(带符号) | `speed`(缺省 60，上限 400)、`release`(缺省 `true` = 走完断电) | `[STEPPER] motor=0 steps=64(CW) speed=60 release=1` → `电机1: 步进 64 步 CW正转` | 该轴转 N 步（**开环、无回零，位置不可靠**） |
| `delay` | `duration` | — | `Delay: 300 ms` | **⚠️ 不会真的等 300ms**，见下方红字 ② |
| `tts`（作 action） | `text` | — | `⚡ [Task] 执行: tts` ｜ `🔊 [PlayTtsDirectly] 播放: …` | **⚠️ 不出声**，见下方红字 ① |
| `emotion`（作 action） | `emotion` | — | `  Emotion: happy`（payload 顶层给 emotion 时才是 `😊 [Command] Emotion: happy`） | 屏上表情变 |

> **⚠️ 红字 ①（本轮新发现的固件事实）**：`PlayTtsDirectly()`（`application.cc:1442-1458`）是**占位实现** —— 只打日志、**不合成音频、不出声**。
> 所以 `payload.tts` / `tts` 动作**不能用来判“设备会说话”**。要它出声只能走**链路 B**（后台 TTS 音频流）。别把 `🔊 播放: …` 当成“说出来了”。
>
> **⚠️ 红字 ②**：`delay` 的 `duration` **不被遵守** —— `StartTaskTimer()` 固定只等 **100ms**（`application.cc:1655`），到点就取下一任务。
> 所以要“间隔 300ms”，只能靠上一条动作自带的 `duration`，或后台自己按时间发（呼吸灯就是这么做的）。
>
> **⚠️ 红字 ③（判固件版本的两句日志，别混）**：
> - `未知动作类型: %s`（`:1436`）= **认识 `command` 通道、但不认识这个动作** ⇒ 固件太旧（例如 10-27 之前没有 `ws2812`）。
> - `Unknown message type: %s`（`:641`）= **连 `command` 这个 root type 都不认识** ⇒ 更老的固件（瓦力那种原厂固件会落这里）。

**老动作（留着不删，后台不要用）**

| 类型 | 位置 | 为什么不用于后台 |
|---|---|---|
| `action`（root type，语义动作如 `move_forward`/`wave`） | `application.cc:524` | 语义写死在固件里，与“固件不写语义”已拍板冲突 |
| `servo` / `move`（作 action） | `ExecuteTask` | 基类是空实现，只有月球车/Doly 覆写；**用 `pwm` 按引脚发** |
| `code_stream`（**root type**，不是 action） | `application.cc:566` | 老入口，`GpioWrite()` 不配输出，已废 |
| `mcp` / `stt` / `llm` / `system` / `alert` / `custom` | 各种 root type | 不是本次下发通路 |

**队列语义（3 条，决定“多条一起发”会不会出错）**

1. 动作**按入队顺序串行执行**，一条没执行完不进下一条。
2. **带 `duration` 的动作用“队尾追加收尾任务”实现**：`gpio` 追加“回低”、`pwm` 追加“占空比 0”、`ws2812` 追加“关灯”，然后延时到点再取队首。
   ⇒ 实际次序是 `A(保持 3s) → 3s → B → A的收尾`，**不是** `A → B → A的收尾`。
3. ⇒ **一次只发一条带 `duration` 的动作**；要连做几件事就分几次发（呼吸灯就是后台每 ~200ms 发一条不带 `duration` 的 `ws2812`）。

**各板支持矩阵**

| 动作 | MOSS `58:E6:C5:5A:2F:FC` | 月球车 `58:E6:C5:58:0C:58` | Doly `58:E6:C5:11:E8:60` | 瓦力 `1C:DB:D4:4C:51:74` |
|---|---|---|---|---|
| `ws2812` | ✅ 实测（GPIO7 / GPIO48） | ✅ 实测（GPIO5，GRB，1 颗） | 支持（未逐项实测） | ❌ 确定不支持（原厂老固件，判据是串口 `Unknown message type: command`） |
| `gpio` / `pwm` | ✅ | ✅ | 支持（未逐项实测） | ⚠️ **未验**（板上是 7-12 原厂固件，而我们 10-26 才加这两个动作，大概率连 `command` 通道都没有） |
| `camera` | ✅ OV2640 实测出帧 | ❌ 固件无 camera 初始化 | 未验 | ❌ |
| `emotion` | ✅ SSD1306 128×64 | ✅ ST7789 | 未验 | ✅ OLED 128×32 |
| 灯的实际引脚 | 7、48 | 5 | 未验 | 无灯（30 脚全扫无反应） |

## 9. 当前基线（2026-11-01 冻结｜**以这一节为准**）

> 用户 2026-11-01 明确：**固件暂时不动了，以现在的状态为基准**。
> 所以下面这份"板上有什么、验过什么、没验什么"就是下一次开工的起点，不必重新摸。

### 9.1 固件（板上 = 源码，一致）

| 项 | 值 |
|---|---|
| MOSS 板上固件 | 含 `ws2812` / `gpio` / `pwm` / `camera` / `delay` / `emotion` / `tts` + **`stepper`**（11-01 新增） |
| `stepper` 语义 | `motor`(0=垂直, 1=水平)、`steps`(带符号)、`speed`(步/秒)、`release`(缺省 true 走完松劲) |
| 执行方式 | 非阻塞：交给板级后按"步数/速度"估时再取下一任务 |
| 存档 | `esp32-firmware\_archive\xiaozhi_moss_stepper_20261101.bin` |
| 回滚点 | `firmware_dumps\moss_flash_16MB_20261031.bin`（原厂整片） |

### 9.2 已实测（可以当结论用）

- 水平轴 = `motor 1`（+ 向左 / − 向右）；垂直轴 = `motor 0`（+ 向后仰 / − 向前俯）
- 标定：**512 步 ≈ 30°** ⇒ 一圈 ≈ **6144 步**（1° ≈ 17 步）；固件上限 ±1024 步 ≈ ±60°
- 垂直轴**断电不回落**（机构自锁）⇒ 不需要靠通电保持力矩
- 灯：`GPIO7` 能亮能灭（`pin=7`）；屏 SSD1306、摄像头 OV2640 驱动在（台账已记）

### 9.3 未验（**不许当结论用**）

| # | 事项 | 缺什么 |
|---|---|---|
| 1 | `GPIO48` 那组灯 | 发绿没亮；查 `H6 ↔ FMH2` 三线（尤其 +5V）/ 灯珠 |
| 2 | `stepper` 高速是否丢步 | 512 步 @ speed=200 看是否仍 ~30° |
| 3 | 月球车/瓦力/Doly 的电机舵机 | 固件里**还没有** `motor`/`servo` 动作（只有 `stepper` 是 MOSS 用的） |
| 4 | `stepper` 的机械安全行程 | 两轴有没有硬限位挡块，未确认 |
