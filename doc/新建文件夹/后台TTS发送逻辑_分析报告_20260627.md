## 1. sendAudioMessage — FIRST/MIDDLE/LAST 的分发

**文件**: `core/handle/sendAudioHandle.py:20-53`

```python
async def sendAudioMessage(conn: "ConnectionHandler", sentenceType, audios, text, sentence_id=None):
    # 跳过旧句子残留音频
    if sentence_id is not None and sentence_id != conn.sentence_id:
        return

    if conn.tts.tts_audio_first_sentence:
        conn.logger.bind(tag=TAG).info(f"发送第一段语音: {text}")
        conn.tts.tts_audio_first_sentence = False

    # ★ FIRST
    if sentenceType == SentenceType.FIRST:
        # 同一句子的后续消息加入流控队列，其他情况立即发送
        if (
            hasattr(conn, "audio_rate_controller")
            and conn.audio_rate_controller
            and getattr(conn, "audio_flow_control", {}).get("sentence_id")
            == conn.sentence_id
        ):
            conn.audio_rate_controller.add_message(
                lambda: send_tts_message(conn, "sentence_start", text)
            )
        else:
            # 新句子或流控器未初始化，立即发送
            await send_tts_message(conn, "sentence_start", text)

    # ★ 发送音频（FIRST/MIDDLE/LAST 都会走这里）
    await sendAudio(conn, audios)

    # 日志
    if sentenceType is not SentenceType.MIDDLE:
        conn.logger.bind(tag=TAG).info(f"发送音频消息: {sentenceType}, {text}")

    # ★ LAST
    if sentenceType == SentenceType.LAST:
        await send_tts_message(conn, "stop", None)
        if conn.close_after_chat:
            await conn.close()
```

### 1.1 三种 SentenceType 的处理对比

| 类型 | `sentence_start` JSON | Opus 音频 | `stop` JSON | 行为 |
|---|---|---|---|---|
| **FIRST** | ✅ 发送（立即或入流控队列） | ✅ 发送 | ❌ | 标记新句子开始 |
| **MIDDLE** | ❌ | ✅ 发送 | ❌ | 仅发送音频 |
| **LAST** | ❌ | ✅ 可能空 | ✅ 发送 | 发送 `stop` 后选择性关闭连接 |

### 1.2 FIRST 发送的两条路径

**路径 A**（流控器已存在且 sentence_id 匹配）：
```
sendAudioMessage(FIRST)
  → audio_rate_controller.add_message(lambda: send_tts_message("sentence_start"))
  → 不 await，后台流控线程稍后执行
```

**路径 B**（新句子/流控器未初始化）：
```
sendAudioMessage(FIRST)
  → await send_tts_message("sentence_start", text)  ← 立即发送
```

**⚠️ 潜在问题**：路径 A 中 `sentence_start` 可能在**音频包之后**才发送（因为音频包通过 `sendAudio` 直接发送，而 `sentence_start` 在流控队列中排队），导致 ESP32 侧的 `sentence_start` 消息晚于 Opus 音频到达，但此问题不影响播放，因为 `sentence_start` 在固件侧仅用于 UI 显示。音频入队的唯一条件是 `device_state_ == kDeviceStateSpeaking`。

## 2. send_tts_message — state="stop" 时的等待逻辑

**文件**: `core/handle/sendAudioHandle.py:266-299`

```python
async def send_tts_message(conn: "ConnectionHandler", state, text=None):
    """发送 TTS 状态消息"""
    if text is None and state == "sentence_start":
        return
    message = {"type": "tts", "state": state, "session_id": conn.session_id}
    if text is not None:
        message["text"] = textUtils.check_emoji(text)

    # TTS播放结束
    if state == "stop":
        # 保存当前的 sentence_id，用于后续判断是否是当前轮次
        current_sentence_id = conn.sentence_id
        # 播放提示音
        tts_notify = conn.config.get("enable_stop_tts_notify", False)
        if tts_notify:
            stop_tts_notify_voice = conn.config.get(
                "stop_tts_notify_voice", "config/assets/tts_notify.mp3"
            )
            audios = await audio_to_data(stop_tts_notify_voice, is_opus=True)
            await sendAudio(conn, audios)
        # ★ 等待所有音频包发送完成！
        await _wait_for_audio_completion(conn)

        # 检查是否是当前轮次
        if current_sentence_id != conn.sentence_id:
            return

        # 停止音频发送循环
        if hasattr(conn, "audio_rate_controller") and conn.audio_rate_controller:
            conn.audio_rate_controller.stop_sending()
        conn.clearSpeakStatus()

    # 发送消息到客户端
    await conn.websocket.send(json.dumps(message))
```

### 2.1 stop 发送的完整流程

```
send_tts_message(state="stop")
  │
  ├── 可选: 播放结束提示音（stop_tts_notify）
  │
  ├── _wait_for_audio_completion(conn)
  │     │
  │     ├── rate_controller.queue_empty_event.wait()
  │     │   └── 等待后台发送循环将队列中的所有音频包发送完毕
  │     │
  │     └── asyncio.sleep(pre_buffer_playback_time)
  │         └── 额外等待预缓冲包播放完成（5+2 个帧 = 420ms）
  │
  ├── conn.audio_rate_controller.stop_sending()
  │
  ├── conn.clearSpeakStatus()  ← 设置 client_is_speaking = False
  │
  └── await conn.websocket.send(json.dumps("stop" JSON))
      └── **"stop" 在音频全部发送完毕后才发出**
```

### 2.3 关键确认

**"stop" 保证在所有音频之后发送**。`_wait_for_audio_completion` 阻塞直到：
- 流控队列清空（所有音频包已发送）
- 额外等待 420ms 预缓冲播放时间

因此 ESP32 固件侧在收到 `"stop"` 之前，已收到所有 Opus 音频包。

## 3. _wait_for_audio_completion — 等待条件可靠性

**文件**: `core/handle/sendAudioHandle.py:56-76`

```python
async def _wait_for_audio_completion(conn: "ConnectionHandler"):
    """等待音频队列清空并等待预缓冲包播放完成"""
    if hasattr(conn, "audio_rate_controller") and conn.audio_rate_controller:
        rate_controller = conn.audio_rate_controller
        conn.logger.bind(tag=TAG).debug(
            f"等待音频发送完成，队列中还有 {len(rate_controller.queue)} 个包"
        )
        await rate_controller.queue_empty_event.wait()

        # 等待预缓冲包播放完成
        frame_duration_ms = rate_controller.frame_duration
        pre_buffer_playback_time = (PRE_BUFFER_COUNT + 2) * frame_duration_ms / 1000.0
        await asyncio.sleep(pre_buffer_playback_time)

        conn.logger.bind(tag=TAG).debug("音频发送完成")
```

### 3.1 条件分支

| 条件 | 结果 |
|---|---|
| `conn.audio_rate_controller` 存在 | ✅ 等待队列清空 + 额外 420ms 休眠 |
| `conn.audio_rate_controller` 不存在 | ❌ **跳过等待，立即发送 "stop"** |

### 3.2 audio_rate_controller 不存在的场景

`audio_rate_controller` 由 `sendAudio()` → `_get_or_create_rate_controller()` 创建，在以下场景可能不存在：

| 场景 | 可能性 | 影响 |
|---|---|---|
| 首个音频包尚未发送 | 低（`sendAudio` 在 FIRST 之前调用） | 首个 `sentence_start` 不会触发 `_wait_for_audio_completion` |
| 没有音频数据（仅发送 ACTION 信号） | 中等 | `sendAudio` 收到空列表直接 return，不创建 controller |
| 异常流程中 LAST 提前到达 | 低 | 无流控器 → **等待被跳过** → "stop" 立即发送 |

**最危险的场景**：

```
chat(depth=0) 进入 → put(FIRST, ACTION)       ← 无音频内容，不创建 rate_controller
LLM 流式处理 → 检测到 tool_call
                → 流式阶段已通知 TTS（部分文字已播报）
                → tool_call 处理 → _handle_function_result
  → 如果是 ACTION.RESPONSE: tts_one_sentence(MIDDLE, TEXT) → 创建 rate_controller
  → 如果是 ACTION.REQLLM:   chat(None, depth+1)
     → depth+1 的 LLM 流式 → MIDDLE → 创建 rate_controller

chat 结束 → put(LAST, ACTION)
  → sendAudioMessage(LAST, [], None)
  → send_tts_message("stop")
  → _wait_for_audio_completion
     → rate_controller 存在 → ✅ 正确等待
```

**但如果 LLM 流式 token 极少，且 TTS 生成极快**：rate_controller 的 `pending_send_task` 可能在 `_wait_for_audio_completion` 之前已完成，这不影响等待，因为 `queue_empty_event` 在队列为空时已设置。

## 4. 速率控制与预缓冲逻辑

**文件**: `core/handle/sendAudioHandle.py:103-131`

```python
async def sendAudio(conn, audios, frame_duration=AUDIO_FRAME_DURATION):
    if audios is None or len(audios) == 0:
        return  # ← 空音频直接跳过

    send_delay = conn.config.get("tts_audio_send_delay", -1) / 1000.0
    is_single_packet = isinstance(audios, bytes)

    rate_controller, flow_control = _get_or_create_rate_controller(conn, frame_duration, is_single_packet)
    audio_list = [audios] if is_single_packet else audios
    await _send_audio_with_rate_control(conn, audio_list, rate_controller, flow_control, send_delay)
```

### 4.1 音频发送的三条路径

```python
# sendAudioHandle.py:227-242
for packet in audio_list:
    if conn.client_abort:
        return

    # ① 预缓冲：前 5 个包直接发送（不经过流控队列）
    if flow_control["packet_count"] < PRE_BUFFER_COUNT:
        await _do_send_audio(conn, packet, flow_control)

    # ② 固定延迟模式
    elif send_delay > 0:
        await asyncio.sleep(send_delay)
        await _do_send_audio(conn, packet, flow_control)

    # ③ 动态流控模式：加入队列，由后台线程以 60ms 间隔发送
    else:
        rate_controller.add_audio(packet)
```

| 路径 | 触发条件 | 发送方式 | 适用场景 |
|---|---|---|---|
| ① 直接发送 | `packet_count < 5` | 立即调用 `websocket.send()` | 前 5 个包快速出站 |
| ② 固定延迟 | `tts_audio_send_delay > 0` | 每次休眠后 `websocket.send()` | 手动配置延迟 |
| ③ 流控队列 | 默认 | 后台线程按帧率发送 | 主流场景 |

### 4.2 预缓冲的副作用

前 5 个包直接从 `sendAudioMessage` 的协程中调用 `websocket.send()`，不经过流控队列。这 5 个包先于流控队列中的包到达 ESP32。

**对 `_wait_for_audio_completion` 的影响**：

```python
pre_buffer_playback_time = (PRE_BUFFER_COUNT + 2) * frame_duration_ms / 1000.0
# = (5 + 2) * 60ms / 1000 = 420ms
```

额外等待 420ms 是为了补偿预缓冲包在客户端播放的时间。这个值是一个估计值，在网络延迟波动时可能不精确，但方向正确（多等比少等安全）。

## 5. 完整的 TTS 发送序列

### 5.1 发送时序图

```
TTS 消化线程 tts_text_priority_thread    _audio_play_priority_thread     WebSocket 网络
──────────────────────────────          ───────────────────────────      ──────────────

消息: (FIRST, ACTION)
  → 重置状态，清空 tts_text_buff
  → 无文本，不入 TTS
                                          ← 音频队列收到 (FIRST, [], None)
                                          → sendAudioMessage(FIRST, [])
                                            → send_tts_msg("sentence_start")
                                                                          {"type":"tts","state":"sentence_start","text":"..."}
                                            → sendAudio([]) 跳过 (空)
                                            → 不等 LAST，无操作

消息: (MIDDLE, TEXT, "你好")               ← (MIDDLE, [opus#1,opus#2,...], "你好")
  → 追加到 tts_text_buff                   → sendAudioMessage(MIDDLE, [opus...])
  → _get_segment_text()                     → sendAudio → 预缓冲5个 + 流控队列
    → to_tts_stream("你好", ...)              → _do_send_audio(opus#1)    → Opus binary #1
      → handle_opus(opus_packet)               → _do_send_audio(opus#2)    → Opus binary #2
        → tts_audio_queue.put(...)              → [流控后台] opus#6...     → Opus binary ...

消息: (MIDDLE, TEXT, "今天天气真好。")
  → 类似流程...

消息: (LAST, ACTION)                      ← (LAST, [], None)
  → _process_remaining_text_stream          → sendAudioMessage(LAST, [])
  → tts_audio_queue.put(LAST, [])             → send_tts_message("stop")
                                                → _wait_for_audio_completion
                                                  → 等待队列清空 → 等待420ms
                                                → stop_sending()
                                                                          {"type":"tts","state":"stop"}
```

### 5.2 发送到 ESP32 的完整 WebSocket 消息序列

```
# 时序 t0
  {"type":"stt","text":"用户说话内容"}           ← STT 确认
  {"type":"tts","state":"start"}                 ← 进入 Speaking

# 时序 t1（TTS 生成完毕，FIRST 处理）
  {"type":"tts","state":"sentence_start","text":"第一句"}

# 时序 t2（音频流）
  Opus binary packet #1                          ← 预缓冲
  Opus binary packet #2
  Opus binary packet #3
  Opus binary packet #4
  Opus binary packet #5
  Opus binary packet #6                          ← 流控队列发送
  Opus binary packet #7
  ...

# 时序 t3（全部 MIDDLE 处理完毕，LAST 处理）
  {"type":"tts","state":"stop"}                  ← 所有音频已发送完毕
```

### 5.3 确认发送序列完整性

| 检查项 | 结果 | 证据 |
|---|---|---|
| `"start"` 是否在音频之前发送 | ✅ 是 | `send_stt_message()` 中先 `send_tts_msg("start")`，TTS 才在后台线程生成音频 |
| `"sentence_start"` 是否在音频之前发送 | ✅ 基本保证 | `sendAudioMessage(FIRST)` 中先 `send_tts_msg("sentence_start")` 再 `sendAudio()` |
| 音频包是否在 `"stop"` 之前全部发送 | ✅ 保证 | `send_tts_message("stop")` 调用 `_wait_for_audio_completion` 阻塞等待 |
| 两句之间的音频是否连续 | ✅ 连续 | MIDDLE 之间不插入 `"stop"` 和 `"start"`，音频连续流式发送 |
| `sentence_id` 在单次 `chat()` 内是否一致 | ✅ 一致 | 顶层 `depth==0` 生成一次，递归 `chat()` 复用相同 ID |

## 6. TTS 音频生成与发送的线程模型

### 6.1 线程/协程关系

```
Asyncio 事件循环（主线程）
┌──────────────────────────────────────────────┐
│  chat() 同步函数 (executor线程池)              │
│    → tts.tts_text_queue.put(TTSMessageDTO)    │  ← 入 TTS 文本队列
│                                                │
│  tts_text_priority_thread (TTS基类线程)         │
│    → tts_text_queue.get()                      │  ← 出 TTS 文本队列
│    → to_tts_stream(text) → TTS API             │  ← 调用 TTS 服务
│    → handle_opus(opus_data)                    │  ← Opus 编码
│      → tts_audio_queue.put((type, audios, ...))│  ← 入音频队列
│                                                │
│  _audio_play_priority_thread (TTS基类线程)      │
│    → tts_audio_queue.get()                     │  ← 出音频队列
│    → sendAudioMessage(...)  (通过 asyncio.run) │  ← 调用 asyncio 发送
│      → send_tts_message("sentence_start")      │
│      → sendAudio() → _do_send_audio()          │
│        → conn.websocket.send(opus)             │  ← WebSocket 发送
└──────────────────────────────────────────────┘
```

### 6.2 关键线程安全点

- `tts_text_queue` 和 `tts_audio_queue` 都是 `queue.Queue()`（线程安全）
- `sendAudioMessage` 通过 `asyncio.run_coroutine_threadsafe` 在主事件循环中执行
- `conn.websocket.send()` 在事件循环线程中调用，符合 asyncio 要求

### 6.3 潜在串行瓶颈

```
TTS 服务调用 (to_tts_stream) → 可能阻塞 0.5-5 秒
  ↓
Opus 编码 (handle_opus) → 较快
  ↓
音频队列 (tts_audio_queue) → 缓冲
  ↓
sendAudioMessage → WebSocket 发送
```

TTS 服务调用是最耗时的环节，但 `_audio_play_priority_thread` 从 `tts_audio_queue` 中消费已生成的音频，与 TTS 文本处理线程并行，不会互相阻塞。

## 7. 结论：后台侧潜在问题

### ✅ 发送序列完整性
1. **`"start"` 先于所有音频**：`send_stt_message()` 在 `startToChat()` 开头发送，TTS 在后台生成
2. **音频全部在 `"stop"` 前发送**：`_wait_for_audio_completion` 保证队列清空后才发 `"stop"`
3. **句子间连续**：MIDDLE 之间无 `"stop"` / `"start"` 插入，状态机不中断

### ⚠️ 仍可能存在的问题

| 问题 | 文件:行号 | 风险 |
|---|---|---|
| `_wait_for_audio_completion` 跳过等待 | `sendAudioHandle.py:63` | 如果 `audio_rate_controller` 不存在，等待被跳过 → `"stop"` 过早发送 |
| `rate_controller` 可能不存在 | `sendAudioHandle.py:134-189` | 若 `sendAudio()` 从未被调用（如只有 ACTION 信号），则不创建 controller |
| **FIRST 的 `sentence_start` 流控入队** | `sendAudioHandle.py:37-38` | 路径 A：`sentence_start` 可能被加入流控队列晚于音频发送，但 `_wait_for_audio_completion` 不等待文本消息，只等待音频 |
| 预缓冲时间固定 420ms | `sendAudioHandle.py:73` | 在网络延迟波动时，预缓冲播放时间可能与实际不同步 |

### 最可能的丢包环节

**后台侧排查结论**：在**正常 TTS 流程（有完整 FIRST + MIDDLE + LAST）**下，后台发送序列是完整且有序的，不太可能导致"只播第一句"。

**需要关注的特殊场景**：
1. **工具调用场景**中 `_handle_function_result` → `tts_one_sentence(MIDDLE)` — 这些 MIDDLE 的文本被 `re.split(r"([。！？!?；;\n])")` 切分。如果切分后某个 `seg` 为空字符串，`to_tts_stream` 会调用一次 TTS 服务生成空音频 → 空 `opus_packet` → 被 `sendAudio` 跳过
2. **句子极短场景**下 FIRST 和 LAST 之间只有极少的 MIDDLE token，在流控队列中可能被快速处理完毕
