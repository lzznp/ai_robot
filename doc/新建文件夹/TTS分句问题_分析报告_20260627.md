# TTS 分句问题分析报告

**日期**: 2026-06-27
**项目**: `D:\study\ai_robot\esp32-firmware`
**问题**: 后台下发多句 TTS（FIRST + MIDDLE + LAST），固件只播放第一句，后续句子被丢弃

---

## 1. 问题描述

服务端在一次 `chat()` 调用中，通过 `TTSMessageDTO` 的 `sentence_type`（FIRST/MIDDLE/LAST）标记多句 TTS 文本。固件表现为**只播放第一句，后续句子被丢弃**。

服务端发送的 WebSocket 序列（正常场景）：
```
{"type":"tts","state":"start"}        ← 触发 Speaking 状态
{"type":"tts","state":"sentence_start","text":"第一句"}
Opus binary (第一句的音频)
{"type":"tts","state":"sentence_start","text":"第二句"}
Opus binary (第二句的音频)
{"type":"tts","state":"stop"}          ← 退出 Speaking 状态
```

预期：两句都播放。实际：只有第一句播放。

| 消息 | 执行方式 | 即时生效？ |

void Application::Schedule(std::function<void()> callback) {

## 3. 根因分析

### 3.1 核心根因：竞态条件（Race Condition）

```
时间轴（WebSocket 任务线程）
──────────────────────────────────────────────────────────────────

 t0: 收到 "tts start" JSON
     → OnIncomingJson → Schedule(SetDeviceState(Speaking))
     → main_tasks_ 队列新增一项回调
     → Schedule 立即返回（不阻塞）

 t1: 收到 Opus 二进制音频（第一句的第一个包）
     → OnIncomingAudio → 检查 device_state_ → 仍然是 OldState！
     → ❌ 丢弃！因为 SetDeviceState 还未执行

 t2: 收到后续 Opus 二进制音频
     → OnIncomingAudio → 检查 device_state_ → 仍是 OldState
     → ❌ 丢弃！

 t3: 主循环 MainEventLoop 获得 CPU 时间片
     → 处理 main_tasks_ → 执行 SetDeviceState(kDeviceStateSpeaking)
     → ResetDecoder()（此时队列为空，无影响）
     → device_state_ = kDeviceStateSpeaking

 t4: 收到后续 Opus 二进制音频
     → OnIncomingAudio → 检查 device_state_ → kDeviceStateSpeaking
     → ✅ 入队 → 解码 → 播放
```

**后果**：在 t1 ~ t3 时间段到达的 Opus 音频包全部被静默丢弃。

**⚠️ 但这无法完全解释"只播第一句"** —— 丢弃的只是最开始的几个包（音频起始部分被切掉），后续包应该正常播放。

### 3.2 补充根因：ResetDecoder 无条件清空

当 `"tts state: start"` 被 Schedule 执行时，`SetDeviceState(kDeviceStateSpeaking)` **无条件**调用了 `ResetDecoder()`。

如果前一轮播放的音频队列尚未清空（例如：播放线程较慢），`ResetDecoder()` 会直接清空解码和播放队列，导致：
```
前一帧残留音频 → 被 ResetDecoder 清空 → 播放中断 → 人耳感知为"只播了第一句"
```

### 3.3 组合效应

```
正常时的 TTS 数据流向：
  server → "start" → [Schedule 延迟] → Speaking → ResetDecoder → Audio入队 → 解码 → 播放

竞态时的实际流向：
  server → "start" → [Schedule 延迟]
  server → Audio包#1 → 状态未变 → ❌ 丢弃
  server → Audio包#2 → 状态未变 → ❌ 丢弃
  [Schedule 执行] → Speaking → ResetDecoder
  server → Audio包#3 → ✅ 入队 → 解码 → 播放
  server → Audio包#4 → ✅ 入队 → 解码 → 播放
  server → "stop" → [Schedule 延迟]
  [Schedule 执行] → Listening
  server → Audio包#5 → ❌ 丢弃 ← "stop" 的先到导致后面的也丢
```

**"只播第一句"的完整解释**：
- 第一句的起始音频包（包#1、#2）因竞态被丢弃
- 第一句的剩余音频（包#3、#4）正常播放 → 人耳听到不完整的第一句
- 如果服务端在句间有微小停顿，或 `"stop"` + `"start"` 分离发送时，`ResetDecoder()` 会清空队列
- 经过多次这样的竞态，**用户感觉只有第一句被播放了**（实际是被切成了碎片）

### 3.4 次要因素：ResetDecoder 在跨句场景的副作用

如果服务端**确实在句子间发送了独立的 `"start"`/`"stop"` 序列**（例如 tool call 场景），
```
"stop" → Listening → (音频队列可能还有未播放完的)
"start" → Schedule → SetSpeaking → ResetDecoder() → ★ 清空队列 → 残留音频丢失
```

## 4. 修改方案建议

### 方案 A（核心修复）：OnIncomingAudio 改用 Schedule 包裹

**目标**：消除竞态条件，确保音频入队时 `device_state_` 已处于正确状态。

**修改文件**：`application.cc:425-428`

```cpp
// ★ 修改前
protocol_->OnIncomingAudio([this](std::unique_ptr<AudioStreamPacket> packet) {
    if (device_state_ == kDeviceStateSpeaking) {
        audio_service_.PushPacketToDecodeQueue(std::move(packet));
    }
});

// ★ 修改后 — 通过 Schedule 保证状态一致性
protocol_->OnIncomingAudio([this](std::unique_ptr<AudioStreamPacket> packet) {
    Schedule([this, packet = std::move(packet)]() {
        if (device_state_ == kDeviceStateSpeaking) {
            audio_service_.PushPacketToDecodeQueue(std::move(packet));
        }
    });
});
```

**可行性**：✅ **必要且充分**

- 消除了 WebSocket 任务线程与主循环线程间的竞态
- `PushPacketToDecodeQueue` 内部已带互斥锁，线程安全
- Schedule 队列处理顺序保证先入先出，`"start"` 调度的 `SetSpeaking` 一定在音频包之前执行

**潜在延迟**：每个音频包多一次主循环调度。`MainEventLoop` 使用 `xEventGroupWaitBits` 实时响应，延迟在 FreeRTOS 任务调度周期内（通常 < 1ms），对 60ms 一帧的 Opus 音频无影响。

### 方案 B（辅助修复）：ResetDecoder 仅在首次进入 Speaking 时清空

**目标**：防止 `ResetDecoder` 在跨句 TTS 时清空仍有音频的队列。

**修改文件**：`application.cc:719-728`

```cpp
// ★ 修改前 — 无条件清空
case kDeviceStateSpeaking:
    display->SetStatus(Lang::Strings::SPEAKING);
    if (listening_mode_ != kListeningModeRealtime) {
        audio_service_.EnableVoiceProcessing(false);
        audio_service_.EnableWakeWordDetection(audio_service_.IsAfeWakeWord());
    }
    audio_service_.ResetDecoder();   // ← 无条件
    break;

// ★ 修改后 — 仅从非 Speaking 状态进入时清空
case kDeviceStateSpeaking:
    display->SetStatus(Lang::Strings::SPEAKING);
    if (listening_mode_ != kListeningModeRealtime) {
        audio_service_.EnableVoiceProcessing(false);
        audio_service_.EnableWakeWordDetection(audio_service_.IsAfeWakeWord());
    }
    if (previous_state != kDeviceStateSpeaking) {    // ← 条件化
        audio_service_.ResetDecoder();
    }
    break;
```

**前提**：`SetDeviceState` 方法中的 `previous_state` 变量已经存在（`application.cc:683`，但当前未被 switch 语句使用）。

**可行性**：✅ **推荐同时实施**

- 消除了 `ResetDecoder()` 在"Speaking → Listening → Speaking"转圈时的误清空
- 保留了首次进入 Speaking 时清空旧音频的正确行为

### 方案 C（服务端配合排查）

**目标**：确认服务端不提前发 `"stop"`。

检查 `connection.py` 中 `chat()` 函数结尾是否只在 `depth == 0` 时发 LAST，`_handle_function_result` 中 `REQLLM` 路径是否未发 LAST。（根据前期分析，服务端行为正常。）
