## 2. 完整的播报流程

### 2.1 总览

```
服务器                            ESP32 固件
  │                                  │
  │  JSON {"type":"tts","state":"start"}  ──►  application.cc:465
  │                                       │  aborted_ = false
  │                                       │  状态 → kDeviceStateSpeaking
  │                                       │  ResetDecoder() 清空残留缓冲(仅非Speaking→Speaking时)
  │                                       │
  │  二进制 Opus 音频帧 ──────────────────►  websocket_protocol.cc:111
  │                                       │  on_incoming_audio_ callback
  │                                       │  application.cc:427-437
  │                                       │  检查 device_state_ == Speaking ? 接受 : 丢弃
  │                                       │  接受的包 → PushPacketToDecodeQueue()
  │                                       │
  │  JSON {"type":"tts","state":"sentence_start","text":"..."}
  │          ──► application.cc:484       │  更新屏幕显示
  │                                       │
  │  ... 更多 Opus 帧 ...                 │
  │                                       │
  │  JSON {"type":"tts","state":"stop"}   │
  │          ──► application.cc:473       │
  │                                       │  状态 → kDeviceStateIdle(手动) 或 Listening(自动)
  │                                       │  ★ 此时解码/播放队列中已有的包会继续播放
  │                                       │  ★ 但后续到达的 Opus 帧会被丢弃！
```

### 2.2 关键路径详情

#### 步骤 A: 收到 `tts start`
- `application.cc:465-472`:
  ```cpp
  if (strcmp(state->valuestring, "start") == 0) {
      Schedule([this]() {
          aborted_ = false;
          if (device_state_ == kDeviceStateIdle || device_state_ == kDeviceStateListening) {
              SetDeviceState(kDeviceStateSpeaking);
          }
      });
  }
  ```
- `SetDeviceState(kDeviceStateSpeaking)` → `application.cc:799-808`:
  - 修改状态为 Speaking
  - 如果 `listening_mode_ != kRealtime`: 关闭语音处理，关闭唤醒词检测
  - 如果 `previous_state != Speaking`: 调用 `ResetDecoder()` 清空残留缓冲

#### 步骤 B: 收到二进制音频帧
- `websocket_protocol.cc:111-145`: `OnData` 回调根据 binary 标志路由
  - binary=true → 封装为 `AudioStreamPacket` → 调用 `on_incoming_audio_()`
  - binary=false → 解析 JSON → 调用 `on_incoming_json_()`
- `application.cc:427-437`: 回调检查状态
  ```cpp
  if (device_state_ == kDeviceStateSpeaking) {
      audio_service_.PushPacketToDecodeQueue(std::move(p));  // 接受
  } else {
      // DROP — 不在 Speaking 状态时丢弃
  }
  ```
- `audio_service.cc:418-429`: `PushPacketToDecodeQueue`
  - 插入 `audio_decode_queue_`（最大 2400ms / 60ms = 40 包）
- `audio_service.cc:301-342`: `OpusCodecTask` 线程
  - 从 `audio_decode_queue_` 取出 → `opus_decoder_->Decode()` → 重采样 → 压入 `audio_playback_queue_`（最大 2 个 PCM 任务）
- `audio_service.cc:265-298`: `AudioOutputTask` 线程
  - 从 `audio_playback_queue_` 取出 → `codec_->OutputData()` → I2S 播放

#### 步骤 C: 收到 `tts stop`
- `application.cc:473-483`:
  ```cpp
  if (strcmp(state->valuestring, "stop") == 0) {
      Schedule([this]() {
          if (device_state_ == kDeviceStateSpeaking) {
              if (listening_mode_ == kListeningModeManualStop) {
                  SetDeviceState(kDeviceStateIdle);      // 手动 → 待命
              } else {
                  SetDeviceState(kDeviceStateListening);  // 自动 → 继续听
              }
          }
      });
  }
  ```
- **注意**: 没有清空解码/播放队列！已有数据继续播放。
- 但新到的 Opus 帧会被丢弃（因为状态已不是 Speaking）。

### 4.1 双缓冲队列管道

### 4.3 播放输出（`audio_service.cc:265-298`）

    while (true) {
        // 等待 playback queue 有数据
        auto task = std::move(audio_playback_queue_.front());
        audio_playback_queue_.pop_front();

        // 如果输出被关闭了，重新打开
        if (!codec_->output_enabled()) {
            codec_->EnableOutput(true);
        }
        codec_->OutputData(task->pcm);  // 写入 I2S
        last_output_time_ = ...;
    }
}

## 5. 播报结束检测机制

### 5.1 固件的播报结束逻辑

| 条件 | 动作 |
|---|---|
| 收到 `tts stop` | Speaking → Idle/Listening；不清空缓冲 |
| 收到 `abort` 信令 | 设置 `aborted_ = true`；发送 abort 到服务器 |
| 唤醒词打断 | `AbortSpeaking(kAbortReasonWakeWordDetected)` |
| WebSocket 断开 | 回到 Idle |

### 5.2 验证结论

**固件完全依赖服务器下发的 `tts stop` 信令来判断播报结束。**

- ✅ "播报完成后自动回到待命模式" — **严格来说不成立**。固件不会自动检测"缓冲区空"或"播放完毕"来切换状态。它等待服务器发 `stop` 信令。
- ✅ 但是 — 即使状态切换到 Idle 后，**已经在队列里的音频数据会继续播放完毕**（队列不清空）。
- ❌ **潜在截断原因**: 如果 `tts stop` 在最后一批 Opus 帧到达之前就下发了，后续的 Opus 帧会因为 `device_state_ != Speaking` 而被丢弃。但缓冲区中已有的数据会播完，所以截断发生在"最后一批帧被丢弃"导致的末尾缺失。
- ❌ 另一个截断点: `ResetDecoder()` 在进入 Speaking 时清空所有队列——如果后台发送 `tts start` 之前还有未播放完的旧数据，都会被清掉。

### 5.3 没有"播报完成"的上报机制

固件**没有**在播报完成后向服务器发送任何通知/回调。状态机切换是单向的——服务器通过 `tts stop` 来"告知"固件结束，而不是固件"通知"服务器。

## 7. 建议：后台如何配合固件播报

### 7.1 `tts stop` 的时机

这是最关键的一点。固件**完全依赖** `tts stop` 来结束播报状态。

- **早发问题**: 如果 `tts stop` 在音频帧全部送达前下发，最后若干 Opus 帧会被固件丢弃（因为状态已切出 Speaking），导致播报末尾缺失。
- **晚发问题**: 如果 `tts stop` 迟迟不下发，固件一直处于 Speaking 状态，无法进入 Listening/Idle，后续交互受影响。

**推荐做法**:
```
┌──────────────────────────────────────────────────┐
│ 1. 先发完所有 Opus 音频帧                         │
│ 2. 确认最后一个 Opus 帧已从 WebSocket 发送完成     │
│ 3. 再发 tts stop                                  │
│                                                   │
│ 如果使用大模型流式 TTS，建议：                      │
│   - 每生成一个句子就立即下发对应的 Opus 帧          │
│   - 在所有句子生成完毕、所有帧发送完成后，再发 stop  │
└──────────────────────────────────────────────────┘
```

### 7.2 `sentence_start` 与音频帧同步

`sentence_start` 是一个纯显示消息，不影响音频播放。服务器可以：
- 在发某句对应的 Opus 帧之前或同时发送 `sentence_start`
- 多个 `sentence_start` 可以在音频播放过程中持续发送

### 7.3 关于截断的排查方向

如果已经出现播报长文本被截断，建议排查：

1. **检查后台是否在 TTS 流结束前发了 `stop`**
   - 这是最常见原因：最后几句的 Opus 帧还没送达就已经发了 stop

2. **检查 Opus 帧的采样率（`sample_rate`）和帧时长（`frame_duration`）**
   - 固件默认期望 `sample_rate=16000` 或 `24000`，`frame_duration=60ms`
   - 如果服务器发来的参数和固件不匹配，可能在解码时出问题（虽然固件会尝试重采样）

3. **检查是否有打断逻辑**
   - 如果用户唤醒词检测触发了 `AbortSpeaking`，播报立即中断

4. **检查 WebSocket 版本**
   - 协议版本1: 直接 Opus 裸数据
   - 协议版本2: 带 `BinaryProtocol2` 头部（含 timestamp）
   - 确保服务器按固件配置的版本号封装数据

### 7.4 `listening_mode` 对行为的影响

后台可以通过固件上报的 `listening_mode` 来了解行为预期：

| 模式 | tts stop 后进入 | 使用场景 |
|---|---|---|
| `manual_stop` | Idle（待命） | 按键触发对话，一次一问一答 |
| `auto_stop` | Listening（监听） | 唤醒词触发，持续对话 |
| `realtime` | Speaking（继续保持说话状态, VAD开启） | 需要 AEC 支持的全双工模式 |

## 8. 总结

1. **固件播报的核心信令**: `tts start` → Opus 帧流 → `tts stop`。没有 start 就不收音频，没有 stop 就不结束。

2. **状态切换是信令驱动的，不是缓冲区驱动**的。固件不会自动判断"播完了"。

3. **截断的根因猜测**（需验证）: `tts stop` 在最后一批 Opus 帧到达之前下发，导致末尾帧被丢弃。

4. **没有播报完成的上报**。如果想确认播报已结束，后台需要根据自己下发的 stop 信令来推断，或者自行在 stop 后等待一段时间确认。

5. **推荐的后台策略**: 在确保所有 Opus 帧已发送完毕后，再发 `tts stop`，并且可以考虑在 stop 和最后一帧之间留 200-500ms 的缓冲时间，避免网络延迟导致帧到达 stop 之后。
